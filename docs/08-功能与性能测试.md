# 功能与性能测试（阶段 9）

> 代码位置：`server/scripts/e2e/`（冒烟）、`server/scripts/bench/`（压测与慢查询复核）
> 本文所有数字都是本机实测输出，没有一条是估算或抄的。

这一阶段要回答四个问题，而不是"跑个分"：

1. 整条链路今天还能不能走通 —— 端到端冒烟，24 步，真实端口 + 真实 socket

3. 一条消息从 `emit` 到对方收到要多久、服务端每秒能吃多少条 —— Socket 压测
4. 数据库有没有慢查询、索引有没有白建 —— EXPLAIN (ANALYZE, BUFFERS) + 统计视图

## 1. 环境与夹具

| 项 | 值 |
|---|---|
| 操作系统 | Windows 11 家庭版 10.0.26200 |
| CPU | Intel i7-13650HX（14 核 / 20 线程） |
| 内存 | 23.8 GB |
| Node.js | v22.22.2 |
| PostgreSQL | 15.10（独立实例，端口 5433） |
| Redis | 5.0.14.1（端口 6379，压测用 db1） |
| 服务进程 | **单进程** `node src/server.js`，`NODE_ENV=development`，无 Nginx |

这三条限制必须写在数字旁边，否则数字会被误读：

- **压测器和被测服务在同一台机器上**，共享 CPU 与内存带宽。压测器本身（Node 进程）在并发 50 时也吃 CPU，所以这里的吞吐是**下限**，延迟是**上限**。
- **单进程 + 单线程**。Node 的 JS 是单线程，PG 连接池 `max: 10`。并发超过 10 以后一定会排队 —— 看到的延迟增长是排队，不是查询变慢。
- **Windows**。定时器精度（约 15ms）与 TCP 栈行为和 Linux 不同，绝对值不要和 Linux 服务器上的数字直接比。

### 1.1 为什么要单独建一个压测库

`chatflow_bench`，与 `chatflow`（开发库）、`chatflow_test`（测试库）完全隔离：

- 压测要灌几万条消息，灌进开发库会毁掉演示数据（截图、录屏全部要重来）
- `scripts/bench/prepare.mjs` 会 `TRUNCATE`，必须有个"可以随便清"的库
- 所有破坏性操作前都校验 `current_database()`，指错库直接报错退出（`lib/benchDb.mjs`）

夹具规模（`--pairs=120 --messages=200`）：

| 项 | 数量 |
|---|---|
| 用户 | 241（1 个 hub + 120 对） |
| 好友关系 | 360 |
| 会话 | 360（120 对私聊 + hub 与每人各一个） |
| 消息 | 48,000 |
| 库大小 | 20 MB |
| **hub 的会话数** | **240** |

hub 是刻意造的"最坏情况账号"：它和 240 个人都有会话，所以 `GET /api/conversations` 对它是一次 240 行的重查询。用它压，是为了让这个接口的代价**无法被数据量小掩盖**。

### 1.2 夹具里两个"作弊"的地方，以及为什么不算作弊

| 做法 | 原因 |
|---|---|
| 用户直接 SQL 插入，共用同一个 bcrypt hash | 走注册接口造 241 个用户，要付 241 次 bcrypt(cost 10，约 70ms/次) + 撞"5 个/小时/IP"限流，等于要跑两天。**登录/注册本身在 HTTP 压测里单独测了**，成本没有被掩盖 |
| token 直接签发，不走登录 | 同上：登录限流 10 次/15 分钟/IP。签名用的是运行时同一个 `JWT_SECRET`，这些 token 是真的，能通过校验 |

## 2. 端到端冒烟：24 步，1.4 秒

`node scripts/e2e/smoke.mjs` —— 和 vitest 用例的区别：vitest 用 `supertest` 直接 `import createApp()`，不起端口；冒烟跑的是**部署形态**，真的 HTTP + 真的 WebSocket + 真的 PG/Redis。

实测输出（`--base=http://127.0.0.1:3200`）：

| 步骤 | 断言点 | 耗时 |
|---|---|---|
| 健康检查 | `db=up redis=up presence=redis` | 141ms |
| 注册 A / B | 201 且返回 token | 150 / 75ms |
| token 换当前用户 | 身份与注册时一致 | 15ms |
| 登录接口 | 第二条身份通道可用 | 75ms |
| 重复注册同邮箱 | 409 `AUTH_EMAIL_TAKEN` | 73ms |
| 搜索用户 | 能找到刚注册的 A | 144ms |
| 发好友申请 | 201，状态 `pending` | 16ms |
| 收件箱 | 申请出现在 A 的 incoming | 12ms |
| 同意申请 | 返回好友是 B | 13ms |
| 打开会话 | 首次 **201** | 50ms |
| 再开同一会话 | **200** + 同一 id（不建第二条） | 7ms |
| 两人建 socket | 握手鉴权通过 | 23ms |
| A 发消息 | ack ok、`duplicated=false`、B 收到同内容同幂等键 | 217ms |
| 幂等重发 | `duplicated=true`、两次同 id、只有一条 | 17ms |
| B 标记已读 | A 收到 `message:read:update`，游标推进 | 10ms |
| 会话详情 | `peerReadUpToMessageId` 已是该消息（推送丢失时的兜底） | 8ms |
| B 断线 | — | 205ms |
| A 在离线期间发消息 | 落库成功 | 5ms |
| B 重连 | 收到 `message:offline`，未读 2 | 13ms |
| `message:sync` | 补到断线期间那条 | 2ms |
| 历史分页 | 第二页全部 `< before` | 7ms |
| 会话列表 | `unreadCount` 与最后一条消息都对得上 | 4ms |
| 越权访问 | 非成员拿到 **404**（不是 403） | 86ms |

第一行那 217ms 是进程内第一次发消息，包含 PG 事务、连接池取连接、推送三条路径的首次执行。后面同类操作都在 5–20ms。

两个细节是刻意保留的写法，不是随手写的：

- **监听必须先于 emit**：服务端是先 `emit` 再回 ack。冒烟里 `waitFor(B, 'message:receive')` 写在 `emitAck` 之前，否则必然超时（`socket.io` 不缓存没人监听的事件）。
- **`message:offline` 要在 `connect` 之前挂**：它在连接建立后立刻推，晚一毫秒就永久错过。

## 3. HTTP 接口压测

`node scripts/bench/http.mjs --iterations=300 --concurrency=1,10,50`

自写的 keep-alive 压测器（`lib/http.mjs`），每档并发 300 个请求（每 worker 300 次，闭环保压），预热按并发跑完再计时。

| 场景 | 并发 | RPS | p50 | p95 | p99 | 错误 |
|---|---|---|---|---|---|---|
| `GET /api/health` | 1 | 870.3 | 1.04 | 1.42 | 1.75 | 0 |
| | 10 | 1,254.6 | 7.84 | 8.78 | 9.38 | 0 |
| | 50 | 1,371.3 | 34.53 | 39.47 | 42.86 | 0 |
| `GET /api/conversations`（hub，240 会话） | 1 | 60.6 | 16.39 | 17.45 | 18.12 | 0 |
| | 10 | 156.0 | 62.84 | 74.06 | 81.72 | 0 |
| | 50 | 159.9 | **303.13** | **338.26** | 341.83 | 0 |
| `GET /api/conversations/:id/messages` | 1 | 373.2 | 2.48 | 3.18 | 4.20 | 0 |
| | 10 | 759.8 | 12.79 | 15.10 | 17.73 | 0 |
| | 50 | 717.1 | 67.00 | 88.49 | 90.66 | 0 |
| `GET /api/friends` | 1 | 131.0 | 7.29 | 8.24 | 8.87 | 0 |
| | 10 | 274.1 | 35.12 | 43.90 | 48.00 | 0 |
| | 50 | 263.1 | 187.50 | 237.37 | 290.71 | 0 |
| `GET /api/users/search?q=` | 1 | 475.7 | 1.99 | 2.47 | 2.76 | 0 |
| | 10 | 1,094.3 | 8.78 | 10.77 | 11.42 | 0 |
| | 50 | 1,114.7 | 45.10 | 50.38 | 54.93 | 0 |
| `POST /api/auth/login` | 1 | 12.8 | 72.70 | 102.52 | 119.46 | 0 |

单位毫秒；登录只有 10 个样本（限流 10 次/15 分钟/IP），所以串行发、只看单发成本。

### 3.1 四个能读出来的结论

**① 吞吐天花板在 ~1,300 RPS，且与业务复杂度无关**

`health` 并发 50 也只有 1,371 RPS。`health` 只做三件事：PG `SELECT 1`、Redis `PING`、读一个字段。所以 1,371 就是"这个单进程 + 这套中间件在本机能达到的上限"。任何业务接口都只能低于它，不可能更高。

**② 并发 10 → 50，RPS 不再增长，延迟线性上升**

| 场景 | RPS @10 | RPS @50 | 延迟 @50 / @10 |
|---|---|---|---|
| conversations | 156.0 | 159.9（+2.5%） | 338 / 74 ≈ 4.6× |
| messages | 759.8 | 717.1（-5.6%） | 88 / 15 ≈ 5.9× |
| friends | 274.1 | 263.1（-4%） | 237 / 44 ≈ 5.4× |
| search | 1,094.3 | 1,114.7（+1.9%） | 50 / 11 ≈ 4.5× |

RPS 不动而延迟按并发比例上升，是小定律（Little's Law）在排队系统里的标准表现：**服务端已经在满负荷，多出来的并发只是在排队**。

这个拐点出现在并发 10 左右，和 `db.js` 里的 `pool max: 10` 对得上：连接池满了以后请求只能等。但要说明的是 —— **连接池是现象，CPU 才是原因**。把 pool 调到 50 只会让 Redis 和 Node 主线程更挤，不会提高吞吐。

**③ 会话列表是最贵的接口，代价与"会话数"线性相关**

hub 有 240 个会话时，并发 1 的 p50 是 16.4ms；120 个会话时同一份代码是 8ms 左右（本轮扩容前的实测）。多出来的时间在 PG 里：

- 每条会话一次 `LATERAL` 取最后一条消息（走 `messages_conv_cursor_idx`）
- 每条会话一次未读 `count(*)` 子查询（同一个索引）
- 一个请求 = 480 次索引扫描

`EXPLAIN ANALYZE` 显示这条查询本身只跑 5.26ms，剩下的 11ms 是 Node 侧的 JSON 序列化（240 条 × ~200 字节）与 Redis 在线状态 pipeline（240 个 Lua 脚本）。

**④ 登录 72.7ms，全是 bcrypt**

`health` 是 1ms，登录是 72.7ms，中间没有数据库压力差异 —— 差距就是 `bcrypt.compare`（cost 10）的 CPU 成本。这决定了登录接口天然是"低 QPS、高单次延迟"的形态，也解释了为什么必须限流：**不限流的话，一个 IP 用 20 个并发就能把这台机器的 CPU 打满，正常用户全部排队**。

## 4. Socket 消息吞吐

`node scripts/bench/ws.mjs --latency-rounds=6 --burst=10,30,60`

测的是写路径的端到端代价：`emit` → 鉴权 session → zod 校验 → 令牌桶 → PG 事务（3 条 SQL）→ 推送 → ack 回来，以及接收方 `message:receive` 的到达时间。

**建连**：212 条 socket（106 对，双方都连）总耗时 650ms，平均 3.07ms/条。

**单发延迟**（6 个用户 × 18 条，串行，108 个样本）：

| 指标 | p50 | p95 | p99 | max |
|---|---|---|---|---|
| ack（落库确认） | 2.73 | 3.28 | 3.93 | 19.35 |
| 投递（对方收到） | 2.66 | 3.21 | 3.71 | 18.98 |

**突发吞吐**（N 个用户同时把配额打完，每人 18 条）：

| 发送者 | 消息数 | 耗时 | 吞吐 | ack p50 | ack p95 | 丢失 |
|---|---|---|---|---|---|---|
| 10 | 180 | 180ms | 997.7 /s | 135.0 | 175.5 | 0 |
| 30 | 540 | 385ms | 1,402.0 /s | 260.1 | 369.7 | 0 |
| 60 | 1,080 | 821ms | 1,315.5 /s | 564.7 | 790.7 | 0 |

1,080 条消息，**投递 1,080 条，0 丢失，0 限流错误**。

### 4.1 读法

- **单人聊天是 2.7ms 的事**。这个数字（含一次 PG 事务）决定了"发送中"状态根本不需要做 spinner —— 前端做了，但实际用户看不到。
- **30 → 60 发送者，吞吐不再增长（1,402 → 1,316），延迟翻倍**。和 HTTP 那边是同一个结论：单进程到顶了。60 个用户的投递仍然零丢失，说明瓶颈是吞吐而不是正确性。
- **每人 18 条不是随便定的**：`messageLimiter` 是 20 条/10 秒/用户。发 18 条留余量；每个阶段用**互不重叠**的用户，否则会撞限流窗口，测出来的是限流器而不是服务端。

## 5. 慢查询复核

`DATABASE_URL=.../chatflow_bench node scripts/bench/sql.mjs`

SQL 直接从 `src/models/*.model.js` 导出的常量取（阶段 9 顺手把内联 SQL 提成了 `export const SQL`），所以 EXPLAIN 的对象和线上执行的是**同一个字符串**，不会漂移。

先跑两次预热再 EXPLAIN，否则冷启动的 `planning time` 会到 90ms（首次访问系统目录），拿它当结论会误判。

| 查询 | 计划 | 执行 | 用到的索引 | 顺序扫描 |
|---|---|---|---|---|
| 会话列表（240 会话） | 1.50 | **5.26** | `messages_conv_cursor_idx` | conversations / conversation_members / users（小表） |
| 会话详情 | 0.32 | 0.10 | `conversation_members_conv_user_uk`、`users_pkey`、`messages_conv_cursor_idx` | conversations |
| 历史分页（limit 31） | 0.06 | **0.03** | `messages_conv_cursor_idx` | 无 |
| 断线补拉（after） | 0.06 | 0.03 | `messages_conv_cursor_idx` | 无 |
| 已读前校验 | 0.05 | 0.02 | `messages_conv_cursor_idx` | 无 |
| 发消息前鉴权 | 0.13 | 0.04 | `conversation_members_conv_user_uk`、`conversations_pkey` | 无 |

`shared read = 0`：全部命中缓存，没有磁盘读。48,000 条消息的库只有 20MB，`shared_buffers` 装得下 —— 这也说明"慢查询"在这个数据量下根本不会出现，能测的只有"计划对不对"。

### 5.1 索引命中（两轮压测后）

| 表 | seq_scan | idx_scan | 说明 |
|---|---|---|---|
| messages | 0 | **504,452** | 全部走索引；`messages_conv_cursor_idx` 单独 502,544 次 |
| conversations | 1,258 | 19,919 | 顺序扫描是 360 行小表，正确 |
| conversation_members | 2,086 | 24,120 | 同上（720 行） |
| users | 5,041 | 2,943 | 241 行，搜索时顺序扫描更便宜 |
| friendships | 2,716 | 1,908 | hub 和 240/360 的人是好友，走索引再回表反而更贵 |

**`messages` 上 `seq_scan = 0` 是这一节最重要的一个数字。** 消息表是唯一会无限增长的表，它没有任何一次全表扫描，意味着分页、补拉、未读统计三条路径都锁在 `(conversation_id, id DESC)` 这一个索引上。

### 5.2 "从未被使用"的 11 个索引，逐个交代

`idx_scan = 0` 不等于没用。三类情况要分开看：

| 索引 | 为什么是 0 |
|---|---|
| 所有 `*_pkey`、`users_email_uk`、`users_username_lower_uk`、`conversations_direct_key_key` | 唯一索引由**约束**维护，`INSERT` 时用它查重，但不计入 `idx_scan` |
| `friendships_incoming_pending_idx`（部分索引） | 只服务"我的待处理申请"。压测没有跑这条接口（它需要真实的申请数据），所以没命中。这条索引的收益在阶段 3 的测试里验证过 |
| `friendships_addressee_idx`、`friendships_requester_idx` | 好友列表的两侧索引。压测用的 hub 在 360 条好友关系里占了 240 条 —— 优化器判断"扫全表更便宜"是对的。它服务的是**好友少、表大**的普通用户，那时才必须走索引 |
| `users_username_trgm_idx` | 见下面的实验 |

trgm 索引这一条值得单独做实验，因为 `GET /api/users/search` 在压测里明明跑了 900 次，索引却 0 次命中 —— 原因是 241 行的小表上，优化器选了 `users_username_lower_uk` 做有序扫描 + `LIMIT 20` 提前终止，比走 GIN 更便宜。

那就造一张 20 万行的表来验证这个索引到底管不管用：

| 计划 | 执行时间 |
|---|---|
| 走 trgm（Bitmap Index Scan） | **0.087ms** |
| 禁掉索引扫描（等价于没建 trgm） | **58.373ms** |

差 670 倍。结论：**这个索引不是白建的，它服务于"关键词罕见 + 用户名很多"的场景**；在当前 241 个用户的数据量下用不上，是因为顺序扫描本来就够了。删掉它，用户量上去那天会变成 58ms 起步的慢查询。

## 6. 会话列表那条判据：要不要加冗余字段

`db/001_init.sql` 在 `conversations` 表上留了一句话：

> 刻意不设 last_message_id 冗余字段 …… 判据: 压测后会话列表接口 P95 > 200ms 再引入冗余字段。

现在的实测数据：

| 条件 | p95 | 是否超过判据 |
|---|---|---|
| 并发 1（单人刷新） | 17.45ms | 否 |
| 并发 10（约 10 个用户同时刷新列表） | 74.06ms | 否 |
| 并发 50（已过饱和，RPS 不再增长） | 338.26ms | **是** |
| PG 执行时间本身 | 5.26ms | — |

**决定：不加。** 理由是这条判据必须带前提，"P95 > 200ms"在并发 50、RPS 已经顶到天花板的饱和状态下必然成立 —— 那是排队时间，不是查询劣化。任何接口在饱和时 P95 都会无限增长，这个判据如果按最坏并发读，等于强制所有人加冗余字段。

真正该看的是**每个请求的固有成本**：5.26ms（PG）+ 约 11ms（序列化与 Redis），对应 240 个会话，约 68µs/会话。要让它超过 200ms，需要约 3,000 个会话/账号 —— 这不是一个聊天产品会出现的数字。

如果哪天真到了那一步，改法也很明确（按性价比排序）：

1. 未读数不再实时 `count(*)`，改成 `conversation_members.unread_count` 计数器（发消息时 +1，已读时清零）—— 省掉 240 次子查询，代价是写放大
2. 再不行才加 `conversations.last_message_id`，并在发消息事务里同步维护（漏更新就会出现"会话列表显示旧消息"，是本项目刻意避开的那类 bug）

## 7. 测试暴露并修掉的两个问题

### 7.1 `/api/health` 在启动后第一次调用返回 `presence: "unknown"`

在线状态的存储模式要等第一个 socket 连上来才确定。监控在服务刚起来时看到 `unknown`，会以为在线状态坏了。

修法：加 `presence.probeStorageMode()`，健康检查自己把结论问出来；`mode` 已经是 `redis`/`memory` 时退化为一次字段读取，不给每次探活加 Redis 往返。修完第一次探活就返回 `presence: "redis"`。

### 7.2 压测器自己制造了 300ms 的"慢查询"

第一次压会话列表，并发 1 的 p50 是 **340ms**，而服务端 SQL 只要 4ms、Redis 2.6ms。

差点据此得出"必须加冗余字段"的错误结论。实际原因是 Nagle 算法 + 延迟确认：30KB 的响应跨多个 TCP 段，服务端等 ACK、客户端 200–300ms 后才回 ACK，两边一起等。`/api/health` 的响应只有一个段，所以完全不受影响 —— 这正是它容易被忽略的原因。

修法：压测客户端的 socket 上 `setNoDelay(true)`，p50 从 340ms 掉到 7.96ms，**服务端代码一行没改**。

这件事本身就是一条经验：**先证明慢的是服务端，再改服务端**。压测工具、网络栈、预热状态都会伪造性能问题。

## 8. 已知限制

| 限制 | 影响 | 什么时候需要处理 |
|---|---|---|
| 单进程，Socket.IO 房间广播不跨进程 | 吞吐上限就是单核 + 事件循环 | 上线后 CPU 长期 > 70% 时加 `@socket.io/redis-adapter` + sticky session，或按用户分片 |
| 压测器与被测服务同机 | 数字偏保守，绝对 RPS 不代表生产容量 | 上云后用两台机器重测一次（ECS + 本地） |
| 登录接口无法做并发压测 | 只有 10 个样本 | 需要时在压测环境临时调高 `loginLimiter`（生产绝不能调） |
| 未测浏览器端渲染性能 | 240 个会话、上千条消息的列表滚动未验证 | 消息超过 200 条/会话时上虚拟滚动 |
| 未测文件上传 | 头像走 Multer，本地磁盘 | 上生产前确认 Nginx `client_max_body_size` 与上传目录权限 |

## 9. 复现

```bash
cd server

# 1. 造压测库与夹具（独立库，不碰开发库）
npm run bench:prepare -- --pairs=120 --messages=200

# 2. 用压测库启动后端（Redis 用 db1，避免和开发库的在线状态串）
PORT=3200 \
DATABASE_URL=postgresql://postgres@127.0.0.1:5433/chatflow_bench \
REDIS_URL=redis://127.0.0.1:6379/1 \
node src/server.js

# 3. 另开一个终端
npm run smoke -- --base=http://127.0.0.1:3200
npm run bench:http -- --base=http://127.0.0.1:3200 --iterations=300 --concurrency=1,10,50
npm run bench:ws   -- --base=http://127.0.0.1:3200 --latency-rounds=6 --burst=10,30,60

# 4. 压测完再做慢查询复核（统计里有真实负载才有意义）
DATABASE_URL=postgresql://postgres@127.0.0.1:5433/chatflow_bench npm run bench:sql
```
