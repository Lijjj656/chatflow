## 2. 为什么单独起一个 PostgreSQL 实例

本机已经有一个 PostgreSQL 15 在 5432 上跑（ThingsBoard 的数据库），但：

- 用默认密码 `postgres` 认证失败，不知道真实密码；
- 那是另一个应用的数据库，不该往里塞项目表；
- 改它的配置（时区、编码）会连带影响 ThingsBoard。

所以做法是：**复用二进制，另起实例**。

```bash
# 数据目录独立，端口独立，认证方式 trust（仅本地开发）
initdb -D D:/chatflow-dev/pgdata -U postgres -A trust -E UTF8 --locale=C
# postgresql.conf 中 port = 5433，timezone = 'UTC'
```

优点：零下载、零侵入、可随时删掉重来。
代价：依赖 ThingsBoard 的安装目录。若卸载了它，把 `scripts/dev-db.sh` 顶部的 `PGBIN` 改指向官方安装目录即可，数据目录不用动。

## 3. 数据库日常操作

```bash
./scripts/dev-db.sh start     # 启动（已运行则跳过）
./scripts/dev-db.sh stop      # 停止
./scripts/dev-db.sh status    # 状态 + 连接串
./scripts/dev-db.sh psql      # 进入 psql
./scripts/dev-db.sh reset     # 删库重建（会二次确认）
```

不想用脚本时，等价的原生命令：

```bash
D=/d/thingsboard/postgresq1/bin
"$D/pg_ctl.exe" -D "D:/chatflow-dev/pgdata" -l "D:/chatflow-dev/pg.log" -w start
"$D/pg_ctl.exe" -D "D:/chatflow-dev/pgdata" -m fast -w stop
```

> 注意：在 Git Bash 里 `pg_ctl start` 会正常后台化。但如果你在**非交互**脚本里启动，
> 进程可能随 shell 退出被杀。真遇到这种情况，改用注册 Windows 服务：
> `pg_ctl register -N chatflow-pg -D D:/chatflow-dev/pgdata`（需要管理员权限）。

## 4. 建表与验证

```bash
cd server
npm run db:init                 # 应用 db/001_init.sql 到两个库
npm run db:init -- --force      # 先删表再建（丢数据）
```

验证唯一性/幂等约束是否真的生效：

```bash
/d/thingsboard/postgresq1/bin/psql.exe -h 127.0.0.1 -p 5433 -U postgres \
  -d chatflow -f ../db/002_verify_constraints.sql
```

该脚本全程在一个事务里跑，末尾 `ROLLBACK`，**可以重复执行**，不会留下脏数据。
它输出 15 条 `PASS` 说明所有约束都真实拦截了非法写入。

> 这个脚本含 psql 元命令（`\echo`），不能用 `npm run db:init` 那种 node pg 客户端跑。

## 5. 启动服务与测试

```bash
cd server
npm run dev        # 默认 3000
PORT=3100 npm run dev   # 3000 被占用时换端口
npm test           # Vitest（串行执行，因为共用一个测试库）
```

### 本地端口占用记录

本机 3000 被一个历史 `node.exe` 占用（不是本项目）。两种处理：

- 临时换端口：`PORT=3100 npm run dev`
- 或者关掉那个进程：先 `netstat -ano | grep :3000` 查 PID，确认是自己的项目再 `taskkill`

## 6. 已知的环境坑

**① 中文用户名导致路径乱码**
家目录是 `C:\Users\李佳恒`。部分 MSYS2 系工具（如 `/usr/bin/ssh`）按 GBK 传路径，会变成乱码目录。
本项目本身不使用这类工具，但如果遇到"路径明明存在却读不到"，先怀疑这个。

**② 环境变量加载**
`src/config/env.js` 用**文件相对路径**解析 `.env`（`server/.env`），不依赖 `process.cwd()`。
所以无论从哪个目录启动都能读到配置。

**③ 时区**
PG 实例 `timezone = 'UTC'`，数据库连接带 `-c timezone=UTC`，所有时间字段是 `TIMESTAMPTZ`。
前端展示时用 dayjs 转本地时区。**不要**在 SQL 里写本地时间字符串。

**④ npm 走国内镜像**
配置在每个项目的 `server/.npmrc`，不污染全局。想全局生效再执行 `npm config set registry https://registry.npmmirror.com`。

## 7. Redis（阶段 6 已落地）

Windows 没有官方 Redis。当时的三个选项：

| 方案 | 说明 |
|---|---|
| Memurai | Redis 兼容的 Windows 服务，免费开发版 |
| **tporadowski/redis** | 社区维护的 Windows 移植版，解压即可用 ← **实际采用** |
| 直接上 ECS | 在 Ubuntu 上 `apt install redis-server`，本地连远程（需注意安全组与密码） |

选移植版的原因：不注册 Windows 服务、不改系统环境，删掉目录就等于卸载干净，
和 PostgreSQL 那套"独立实例 + 独立数据目录"的思路一致。

### 实际落地的配置

| 项 | 值 |
|---|---|
| 二进制 | `D:\chatflow-dev\redis\redis-server.exe`（5.0.14.1） |
| 配置文件 | `D:\chatflow-dev\redis.conf` |
| 数据目录 | `D:\chatflow-dev\redis-data` |
| 端口 | 6379，只绑 `127.0.0.1` |

启动 / 连通性验证：

```bash
D:/chatflow-dev/redis/redis-server.exe D:/chatflow-dev/redis.conf   # 前台启动
D:/chatflow-dev/redis/redis-cli.exe ping                            # → PONG
D:/chatflow-dev/redis/redis-cli.exe -n 1 keys '*'                   # 1 号库 = 测试库
```

`redis.conf` 里几个刻意的选择：

| 配置 | 值 | 理由 |
|---|---|---|
| `appendonly` | `yes` + `everysec` | 在线状态是瞬时数据，但限流计数重启后不能清零（否则重启就能绕过限流） |
| `maxmemory-policy` | `noeviction` | **不做 LRU 淘汰**：静默丢 key 会让"在线"随机丢失，宁可写入报错暴露问题 |
| `maxmemory` | `128mb` | 在线状态 + 限流计数远小于此，触发上限说明有泄漏 |
| `save` | `""` | 关掉 RDB 快照，减少磁盘抖动（已有 AOF） |
| `databases` | `16` | 测试用 `1` 号库，与开发环境 `0` 号库隔离 |

> 测试跑 `1` 号库不是洁癖：`presence.reset()` 会 `SCAN + DEL 'presence:*'`，
> 共用 0 号库会把本机正在跑的开发服务的在线状态一起清掉——
> 症状是"自己电脑上好友头像突然全变灰"。

Redis 不可用时服务仍能启动：`checkRedis()` 返回 `down`，在线状态锁定降级为进程内存
（单实例可用，多进程不互通）。详见 [`05-Redis在线状态.md`](05-Redis在线状态.md) §6。

## 8. 部署到阿里云 ECS 时要改的地方

1. `.env`：`NODE_ENV=production`，`NODE_ENV=production` 下堆栈不再返回给客户端
2. `JWT_SECRET` 重新生成：`openssl rand -hex 32`
3. `DATABASE_URL` 指向本机 PG（建议建独立系统用户，不要用 postgres 超级用户）
4. Nginx 必须配 WebSocket 升级头（详见架构文档风险 2）
5. PM2 用 **fork 单实例**，不要 `-i max`（详见架构文档风险 3）
6. 2 核 2G 需要加 swap 并下调 PG / Redis 内存参数（详见架构文档风险 1）
