# 06 · 离线消息与已读状态

阶段 7 的设计与实测记录。

需求原文有两条：**「离线消息」** 和 **「已读状态」**。这一阶段真正要做的事，
是把阶段 5 留下的三个缺口补上 —— 不是重建已有功能。

| 缺口 | 症状 | 后果 |
|---|---|---|
| 上线不推未读 | 客户端必须自己 `GET /conversations` | 多端冷启动漏拉就是空白角标；拉取与 socket 推送并发，可能互相覆盖 |
| 已读只通知对方 | `deliverReadReceipt` 只 emit 给 peer | 手机读完，电脑角标不清零 |
| 对方读游标不可查 | 会话 DTO 没有这个字段 | 已读回执丢失（对方正好断线）就永久不准，没有自愈路径 |

---

## 1. 「离线消息」不建表

先说结论：**没有离线消息表，也不记 `users.last_seen_at`。**

离线消息的定义就是：

> 此刻所有会话里 `id > 我的读游标`、且不是我发的消息 —— 也就是**未读消息**。

为什么不额外区分"离线期间收到的"和"在线时没看的"：

1. **对用户是同一件事**。他要做的就是"打开看看"，区分了没有任何交互价值。
2. **要区分就得引入第二个真相**。存一个"最后在线时间"，然后拿消息时间和它比 ——
   那"用户挂后台但没断线"算在线还是离线？"断线 3 秒又连上"算不算离线？
   这类边界会衍生出无穷的判定分支，而每个分支都是一个 bug 候选。
3. **一套数字，三种语义**。有了 `last_read_message_id`，未读数、离线消息、已读状态
   全部由同一个数字推导。不存在"消息未读但不在离线列表里"这种自相矛盾的状态。

这就是为什么 `db/001_init.sql` 里只有 `conversation_members.last_read_message_id`，
没有 `message_reads` 表、没有 `offline_messages` 表。

> 反过来说：如果产品真需要"离线消息单独保留 N 天然后清理"，
> 那才需要一个独立的表，因为它的生命周期和消息本体不同。当前需求没这一条。

## 2. 上线推汇总：`message:offline`

连接建立后，服务端主动推一次。

```json
{
  "totalUnread": 5,
  "truncated": false,
  "conversations": [
    {
      "id": 12,
      "peer": { "id": 7, "username": "bob", "online": false },
      "lastMessage": { "id": 987, "content": "在吗", "senderId": 7 },
      "unreadCount": 3,
      "peerReadUpToMessageId": 985
    }
  ]
}
```

### 2.1 为什么推汇总，不推消息本体

离线 3 天可能有 500 条消息。全推一遍：

- 单个 socket 帧可能几 MB，移动端要卡一下
- 用户 99% 只点开其中 1 个会话，其余 499 条白传
- 大帧还会影响同一条连接上其他事件的延迟（head-of-line blocking）

所以推"哪个会话有几条 + 最后一条是什么"（够渲染角标和预览），
用户真正点进去时再用 `message:sync` 拉那个会话的本体。

### 2.2 只推有未读的会话

用户有 50 个会话但只有 2 个有未读，把 50 个都推一遍是纯噪声。
`unreadSummary()` 直接 `filter(unreadCount > 0)`。

这带来一个必须写进协议的事实：**`message:offline` 不等于会话列表**。
要渲染完整的会话列表（包括全读过的），仍然要调 `GET /conversations`。

### 2.3 上限 100 个会话

`OFFLINE_SUMMARY_LIMIT = 100`。超出时 `truncated: true`，客户端应退回 REST 拉全量。

不做这个上限，一个重度用户（几百个会话都有未读）会在连接瞬间收到几百 KB 的帧。
上限比"分页"简单，而且 100 个有未读的会话已经远超正常人的处理能力。

### 2.4 无未读时**不发**事件

不是发一个空数组。理由：

- 客户端为此要多写一条"收到空汇总"的分支
- 没有未读时不需要任何 UI 变化，白占一帧
- "没收到"和"收到空的"对客户端是可区分的（后者反而要额外判断）

### 2.5 每台设备各推一份

不做"每个用户只推一次"的优化。每台设备都需要自己的初始状态：
手机上已读的会话，电脑刚打开也必须显示成已读 —— 而且这个"已读"来自
服务端游标，不是本地缓存，所以必须从服务端拿。

## 3. 已读状态

### 3.1 存储：一个数字，不是 N 行记录

`conversation_members.last_read_message_id`（读游标）。

```sql
UPDATE conversation_members
   SET last_read_message_id = GREATEST(COALESCE(last_read_message_id, 0), $messageId)
 WHERE conversation_id = $1 AND user_id = $2
```

- `GREATEST`：游标只增不减。乱序到达（先标 105 再补标 100）不会回退，
  否则用户会看到"读过的消息又变成未读"。天然幂等。
- `COALESCE(..., 0)`：显式表达"没读过 = 0"。让后续 `id > 游标` 的比较不会遇到 NULL
  （`id > NULL` 恒为 NULL，未读数会静默变成 0，是这个查询最容易埋的坑）。

**为什么不用 `message_reads` 表**（`(message_id, user_id)` 一行一条）：
进一个有 200 条未读的会话，就会产生 200 行写入，而信息量只有 1 个数字。
游标方案把写入量从 `O(未读数)` 降到 `O(1)`，读取也只多一个字段。
微信的双蓝勾就是这个模型：`对方游标 >= 这条消息 id` → 已读。

### 3.2 三处一致性

| 场景 | 靠什么保证 |
|---|---|
| 我的未读数 | 会话列表 SQL 里 `count(*) WHERE id > 我的游标 AND sender_id <> 我` |
| 对方是否已读我的消息 | `对方游标 >= 我的消息 id` |
| 别的设备的未读 | 服务端推 `message:read:update` 给**读者自己的其它设备** |

第三条是本阶段修的 bug。之前 `deliverReadReceipt` 只 emit 给 peer：

```js
// 修复前
if (!peerId) return;
emitToUser(peerId, 'message:read:update', { ... });
```

用户在手机上读完一个会话，电脑端那个"3"还挂着，直到电脑自己去拉一次会话详情。
这是多端产品里最容易被用户发现的 bug 之一——"我手机上明明看过了"。

修复后推给两类人：

```js
// 读者自己的其它设备（排除发起连接，避免回声）
socket ? emitToUserExcept(socket, readerId, ...) : emitToUser(readerId, ...);
// 对方
if (peerId) emitToUser(peerId, ...);
```

客户端靠 `payload.userId === 自己` 区分语义：自己别的设备在读 → 清自己的角标；
对方在读 → 更新对方的已读位置。同一个事件名，两种处理，因为底层是同一个事实
（"某个人的游标推进了"）。

### 3.3 回执丢失怎么办：`peerReadUpToMessageId`

WebSocket 推送是**尽力而为**。对方断线时那条 `message:read:update` 直接丢掉，
而且不会补发 —— 传统消息系统在这里就永久不准了。

所以会话 DTO 里必须有这个字段：

```json
{
  "id": 12,
  "unreadCount": 0,
  "peerReadUpToMessageId": 985
}
```

```sql
-- CONVERSATION_SELECT 里加一列
ocm.last_read_message_id AS peer_last_read_message_id
```

客户端在**重连后**、**进入会话时**重新拉一次会话详情，就能把已读位置对齐。
推送负责实时性，REST 负责正确性 —— 两条路都要有，缺一条就会出现
"平时正常，偶尔永久错位"这种最难复现的问题。

> 这条也是本阶段测试里明确验证的：`对方断线期间读过的消息，重连后仍能查到`。

## 4. 事件时序

```
connect
  ├─ join user:<id>
  ├─ registerHandlers（同步，必须最先）
  ├─ presence.addConnection
  │    └─ becameOnline → 广播 user:online 给在线好友
  ├─ sendInitialPresence → 逐个 user:online（当前在线的好友）
  └─ pushOfflineSummary  → message:offline（若有未读）
```

`message:offline` 放在最后：它要查一次会话列表（几十个会话的聚合），
比 Redis 里的在线状态慢得多。先让在线状态可见，再补未读角标，用户感知上更顺。

## 5. 测试

`tests/offline.test.js`（12 项）：

| 分组 | 用例 |
|---|---|
| 离线消息 | 离线期间收到 3 条，上线收到 `totalUnread=3` 与会话明细 |
| 离线消息 | 只汇总有未读的会话，全读过的会话不出现 |
| 离线消息 | 没有未读时不推事件 |
| 离线消息 | 自己发的消息不计入自己的未读 |
| 离线消息 | 多端各自收到一份 |
| 离线消息 | 已读全部后重连，不再收到 |
| 多端已读 | 一台设备读 → 自己的其它设备 + 对方都收到，发起端不收到 |
| 多端已读 | 只影响对应会话 |
| 读游标 | 新会话的对方游标是 0 而不是 null |
| 读游标 | 对方读后能在会话详情看到推进，自己未读清零 |
| 读游标 | 乱序标记已读不回退（REST 看到的也是较大值） |
| 读游标 | 对方断线期间读的，重连后仍能查到（回执丢失可自愈） |

### 写测试时踩的坑：`waitFor` 会漏事件

第一版这么写：

```js
await emitAck(phone.socket, 'message:read', { ... });
const update = await waitFor(laptop.socket, 'message:read:update');   // 超时
```

超时原因是**服务端先 emit 回执、再返回 ack**。`emitAck` resolve 的时候
回执早就到了，而 `waitFor` 是这时才挂 `socket.once` —— socket.io 不缓存事件，
没人监听就直接丢。

改成"在 connect 之前就挂好收集器"：

```js
const laptop = await connectCapturing(b.token, ['message:read:update']);
// 之后读 laptop.log.get('message:read:update')
```

同一个坑在 `message:offline` 上更致命：它是连接建立后**立刻**推的，
用 `connectClient` 再 `waitFor` 必然偶发失败，且失败率取决于机器快慢——
最难查的那类。所以 `connectCapturing` 在 `ioClient()` 之后、`connect` 事件之前
就把监听挂好。

## 6. 已知限制

1. **`message:offline` 只推一次 / 每条连接**。连接期间新增的消息靠 `message:receive` 实时推，
   socket 断开期间的靠下次上线汇总。**没有"补发漏推"机制** —— 如果连接没断但推送丢了
   （极端网络情况），客户端不会自己发现。要彻底解决需要客户端定期对账（拉 `GET /conversations` 比对未读数）。
2. **`peerReadUpToMessageId` 只对单聊有意义**。群聊里"对方"是 N 个人，需要 per-member 游标列表，
   当前 `ocm` 的 LEFT JOIN 写法会命中多行 —— 真做群聊时这块要重写。
3. **没有"已送达"语义**。消息只有"已读/未读"两态。要做"送达"必须由接收端 ack 才算数，
   要么加一张 per-message per-user 的表，要么再加一个 `last_delivered_message_id` 游标。
   当前不做：它和读游标是两套语义，一起上会让"未读"的定义变模糊。
4. **`unreadSummary` 每次连接都跑一次会话列表查询**。100 个会话的用户重连 10 次就是 10 次聚合查询。
   当前规模（作品集）不是瓶颈；量大时应加缓存或改成"客户端上报本地版本号，没变就不推"。
