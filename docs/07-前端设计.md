# 前端设计（阶段 8）

> 技术栈：Vue 3（`<script setup>`）· Vite · Vue Router · Pinia · Axios · Socket.IO Client · 原生 CSS
> 代码位置：`client/`，约 5400 行（含 294 行测试）

这一阶段的目标不是"把接口画出来"，而是把后端已经做好的三件事在界面上**做对**：
消息从哪来、状态归谁管、出错时用户看到什么。

---

## 1. 三个前提性取舍

| 取舍 | 决定 | 理由 |
|---|---|---|
| UI 组件库 | **不用**（Element Plus / Ant Design Vue 一律不引） | 需求指定原生 CSS。更重要的是：组件库会把"布局与状态"的复杂度藏起来，而这两块正是要展示的能力 |
| 状态管理 | Pinia，**按领域切 4 个 store**，不做一个大 store | 认证 / 好友 / 会话消息 / 提示，四者的生命周期完全不同：登出要清 chat 但保留 toast，好友刷新不该影响消息缓存 |
| 请求层 | 只有一个 `api/http.js`，组件**禁止**直接 import axios | 否则 token 注入、错误归一、401 处理会散落十几处，漏一处就是线上事故 |

样式用 CSS 变量做设计令牌（`styles/tokens.css`），组件里不出现裸色值：
换主题只改一个文件，不用全项目搜 `#fff`。

### 1.1 视觉体系

刻意避开"品牌紫 + 大圆角 + 卡片阴影"这套默认长相 —— 那套组合的气味太明显，
一眼就能看出是生成的界面，而不是有人真的做过取舍：

| 决定 | 理由 |
|---|---|
| 主色就是**近黑**，不引入彩色品牌色 | 彩色大按钮、渐变头像是自动生成界面最显著的标记。没有品牌色时，层次只能靠字重、留白和 1px 线建立，界面会安静很多 |
| 底色**偏暖**（`#f2f1ee`，不是 `#f7f8fb` 的冷蓝灰） | 冷灰配白卡片像 SaaS 后台，暖灰更像编辑器或纸张 |
| 圆角 **6–10px**，不用 14–18px | 大圆角 + 大留白是移动端 2019 年的语汇；桌面工具收紧圆角会利落得多 |
| **1px 线分区**，几乎不用阴影 | 阴影只留给真正浮起来的层（弹窗、toast）。满屏阴影会让界面变"糊" |
| 只有**两个语义色**：红（未读/危险）、绿（在线） | 颜色越少，信息密度越显得高；也避免"每个状态一个颜色"的模板感 |
| 时间戳、计数用**等宽字体** | 数字不跳动，同时给纯灰界面加一点排版的质感 |
| 不做左侧"三个图标卖点"的登录页 | 一个登录页只需回答"这是什么"和"怎么进去"。说得越多越像落地页模板 |

组件层的一致性靠三类原子样式兜住：`.btn`（primary/ghost/soft/danger）、
`.input`/`.search`、`.avatar`/`.badge`/`.empty`，其余全部写在组件自己的 `<style scoped>` 里。

## 3. 实时层：连接状态机

`socket.js` 是唯一持有连接的地方。它**不含业务判断**——只知道"连上了/断了/被踢了"，
然后把事件转发给订阅者。业务反应（补拉、清角标、跳登录页）在 store 里。

```
                 ┌──────────── connect_error(AUTH_*) ────────────┐
                 ▼                                               │
  idle ──connect()──> connecting ──connect──> online             │
                          │                    │                 │
                          │                disconnect           auth-failed
                          │              (transport close)        │
                          ▼                    ▼                 │
                      reconnecting <──────── reconnecting        │
                          │                                        │
                          └── connect (recovered=true) ──> online ─┘
```

四个必须区分的断开原因（实测出来的，不是猜的）：

| reason / code | 含义 | 客户端反应 |
|---|---|---|
| `transport close`、`ping timeout` | 网络问题 | 显示"正在重连"，socket.io 自动退避 |
| `io server disconnect` | 服务端主动踢（发版重启等） | **不会自动重连**，需要自己判断要不要 `connect()` |
| `AUTH_*` 握手失败 | token 无效/过期 | 关掉重连、登出、跳登录页 |
| `auth:expired` 事件 | 服务端按 `exp` 到点踢人 | 同上，且不再重试 |

关键实现：`auth` 用**函数形式**传给 socket.io

```js
io({ auth: (cb) => cb({ token: getToken() }) });
```

对象形式 `auth: { token }` 只在创建时求值一次。用户重新登录后，重连带上去的还是旧 token，
表现为"重新登录了却一直连不上"，而错误信息看起来像后端故障。

### 上行调用统一带 ack

```js
socket.timeout(10_000).emit(event, payload, (err, body) => { ... });
```

没有 `timeout` 的 ack 在服务端不响应时会**永久 pending**：用户看到按钮一直转，
控制台没有任何错误。超时后转成 `RealtimeError`，交给 UI 决定重试还是提示。

## 4. 消息：四个来源合成一个列表

| 来源 | 触发时机 | 特点 |
|---|---|---|
| `GET /conversations/:id/messages` | 进入会话 / 上滑加载更早 | 分页、带 `hasMore` |
| `message:receive` | 对方发送，或自己其它设备发送 | 只含一条，可能乱序到达 |
| `message:sync` | 重连后按最后一条 id 补齐 | 可能一次几十条 |
| **本地乐观插入** | 用户按下发送的瞬间 | 还没有服务端 id |

四者收敛靠 `utils/messages.js` 的三个纯函数（`mergeMessage` / `mergeMessages` / `isSameMessage`），
合并在 store 里只负责"什么时候调"。**纯函数是为了能测**——这是全前端最容易出 bug 的地方，
39 个用例里有 20 个都在测它。

### 去重规则

| 情况 | 判定 | 处理 |
|---|---|---|
| 同 `id` | 同一条 | 用服务端字段覆盖本地，保留 `localId` |
| 一方无 `id`，`clientMessageId` 相同 | 乐观消息 vs 服务端确认 | 认领替换，`status: pending → sent` |
| 两条都有 `id` 且不同 | 一定是两条 | **不合并**，即使 `clientMessageId` 撞了 |

第三条看起来多余，但它是必须的：极端情况下两个设备用了同一个客户端 UUID，
按 `clientMessageId` 合并会把真实存在的消息吞掉。

### 发送：两条通道 + 同一个幂等键

```
按下 Enter
  ├─ 立刻插入占位消息（status: pending），清空输入框
  ├─ socket.emit('message:send', { conversationId, content, clientMessageId })
  │     ├─ ack ok      → 用返回的消息替换占位（靠 clientMessageId 认领）
  │     └─ OFFLINE / ACK_TIMEOUT
  │           └─ 退回 HTTP POST /conversations/:id/messages，**幂等键不变**
  └─ 失败 → 占位消息标红，点击气泡侧边「重试」（复用同一个幂等键）
```

**为什么幂等键必须复用**：socket 其实已经落库、只是 ack 在途中丢了 —— 这是最常见的超时场景。
换一个新键重发就会产生两条一模一样的消息；用同一个键，HTTP 这次会被唯一索引拦住，
服务端返回已存在的那条（`duplicated: true`），界面只更新状态。

**为什么先清空输入框**：等 `await` 再清空，用户会看到文字停留 0.3 秒以为没发出去，
于是再点一次（然后又产生一次重复发送）。失败的消息留在列表里点一下就能重试，信息没丢。

## 5. 未读与已读：谁是权威

未读数是"最容易看起来对、实际一直错"的一类状态。这里的规则只有一条：

> **服务端是权威，本地只做即时反馈，重连后一定对齐。**

| 事件 | 本地动作 | 是否需要向服务端对账 |
|---|---|---|
| 收到消息且会话未打开 | `unreadCount + 1` | 不需要（下次拉列表会覆盖） |
| 打开会话 | 立刻清 0 + 发 `message:read` | 不需要 |
| 自己的其它设备已读 | 清 0（`payload.userId === 我`） | 不需要 |
| 对方已读 | 更新 `peerRead[convId]`，只增不减 | 不需要 |
| 重连 | `message:sync` 补消息 + `GET /conversations` 重拉未读 | **是**，断线期间的推送全丢了 |

`peerRead` 用于渲染"已读/未读"：某条我发的消息已读 ⟺ `peerRead >= 该消息 id`。
它有两个来源，缺一不可：

1. `message:read:update` 推送 —— 实时
2. 会话 DTO 的 `peerReadUpToMessageId` —— 回执丢失后的对账依据

### 一个实测发现并修掉的问题

进入会话时角标先清零、一秒后又冒回来。原因是没有考虑**快照的时间差**：

`message:offline`（和 `GET /conversations`）里的 `unreadCount` 是**我点开会话之前**算出来的；
它晚到一步，就会把刚清掉的 0 又覆盖成 1。修法是 `reconcileActiveUnread()`：
合并完列表后，如果当前打开的会话仍有未读、且页面可见，直接清 0 并补发一次已读。

## 6. 交互细节（这些决定了"能不能用"）

| 细节 | 做法 | 不做会怎样 |
|---|---|---|
| 中文输入法 | `compositionstart/end` 标志 + `event.isComposing` | 打"你好"时按 Enter 选词，结果把拼音发出去了 |
| 上滑加载更早 | 记录 `scrollHeight` 差值，插入后补 `scrollTop` | 加载完历史，视野直接跳到中间 |
| 正在看历史时来新消息 | 不抢滚动条，底部浮出「有新消息」 | 这是 IM 最招人烦的 bug |
| 自动跟随 | 只在"用户本来就在底部"或"自己刚发的"时才滚到底 | 每来一条就拽回底部，没法读历史 |
| 消息分组 | 同人 5 分钟内：只显示一次头像、不留时间行 | 一屏全是头像和时间戳 |
| 会话切换草稿 | 按会话 id 存在 Map 里 | 切走再回来，打了一半的字没了 |
| 头像降级 | 图片 404 → 自动退回文字头像 | 显示破图 |
| 时间格式 | 今天 `14:32` / 昨天 `昨天 14:32` / 更早 `11月5日 14:32` | 用 `toISOString()` 截取，显示的是 UTC 时间 |
| 未读上限 | `99+` | 三位数撑破角标 |

## 7. 错误处理策略

统一成一个 `ApiError`（`code / message / status / details`），**按 code 分支，绝不匹配中文文案**。

| 场景 | 判定 | 用户看到 |
|---|---|---|
| 凭证失效 | `401` 且 code ∈ `AUTH_REQUIRED / AUTH_INVALID_TOKEN / AUTH_TOKEN_EXPIRED` | 清 token、跳登录页、提示"登录已过期" |
| 登录密码错 | `401` + `AUTH_INVALID_CREDENTIALS` | 表单内联错误（**不登出**，本来就没登录） |
| 字段校验 | `400` + `details[{field,message}]` | 错误贴到对应输入框下方 |
| 限流 | `429` + `RATE_LIMITED` | "发送太频繁了，请稍等" |
| 网络断/超时 | `status === 0` | "连接不上服务器，请确认后端已启动" |
| 断网（socket） | `OFFLINE` / `ACK_TIMEOUT` | 自动退回 HTTP 通道重试 |

`details` 的结构与后端 zod 输出一致，所以"用户名被占用"这类错误能直接落到输入框上，
不用前端自己维护一份文案映射。

## 8. 实测记录（真实跑过的，不是推测）

用无头浏览器（Edge + puppeteer-core，脚本不入仓库）跑了完整流程：登录 → 会话 → 发消息 →
双端实时接收 → 通讯录 → 加好友 → 同意申请 → 移动端窄屏。

| 验证项 | 结果 |
|---|---|
| 登录 / 注册 / 刷新恢复登录态 | ✅ |
| 会话列表、未读角标、点开后清零 | ✅（角标 `1` → 点开 → `1.5s` 后仍为空） |
| 发消息（socket 通道，乐观渲染） | ✅ |
| 双端实时接收 | ✅ 第二个窗口 1.2s 内出现新气泡 |
| **断网 → 服务端来消息 → 恢复网络** | ✅ 自动补上，气泡数 15 → 16，内容与库里一致 |
| 搜索用户 → 发申请 → 对方同意 | ✅ 按钮 `添加 → 已发送`，对方「新的朋友」可同意 |
| 移动端 430×860 布局 | ✅ 列表/聊天互斥切换，输入框不被遮挡 |
| 浏览器控制台报错 | 0（断网期间的 `WebSocket connection failed` 属于预期） |

### 过程中发现并修掉的问题

1. **未读角标回弹** —— 见 §5，`message:offline` 的旧快照覆盖了新状态。
2. **消息列表没有底部锚定** —— `justify-content` 没处理，消息少时全挤在顶部，
   底部一大块空白。改成 `.list-top { margin-top: auto }`（内容溢出时自动退化为 0，不影响滚动）。
3. **每条消息下面都挂一行时间** —— 即使 `opacity: 0` 也占 16px 高度，十几条消息就是一片空隙。
   时间改为气泡**侧面**、悬停才出现，已读状态只在"我发的最后一条"下面显示。

### 一个有意思的"失败"

联调脚本连跑多次后，登录接口开始返回 `429`：后端限流是 **15 分钟 10 次/IP**。
这不是 bug，恰恰证明限流在工作。测试时要么重启后端（内存计数清零），要么直接复用 token。

### 后端回归

本阶段没有改动后端代码，但仍按文件分批重跑了一遍，合计 **188 项通过**
（认证/用户/健康/数据库/限流 56 + 会话 36 + 好友 37 + 实时 31 + 离线 12 + 在线状态 16），
与阶段 7 结束时的数字一致。

> 分批复跑的原因：本机环境会把连续运行超过 ~90 秒的命令回收，全套一次跑约 3.5 分钟会被打断。
> 分批的结果相加与全量一致，这不是"跳过测试"。

## 9. 已知限制

- **好友申请没有实时推送**。后端只做了消息层的 socket 事件，申请/同意靠前端 30 秒低频轮询
  （只在标签页可见时跑）。要做到即时，需要在 `friend.service` 里加 `friend:request` / `friend:accepted` 事件。
- **不支持图片消息**。后端 `messageType` 只放开了 `text`，图片要等上传通道与消息类型一起扩。
- **没有虚拟滚动**。会话里消息一次性最多加载 30 条、上滑再补，几百条以内没问题；
  上千条需要换成窗口化渲染。
- **草稿只存在内存**，刷新页面会丢。
- **不支持群聊**（后端就没做），所以 `peer` 一定存在，气泡布局没有处理多人群聊的场景。
- **修改密码后 socket 连接仍然有效**（沿用后端的取舍：JWT 只按 `exp` 判断）。
- 消息搜索只过滤**本地已加载的会话**，不是服务端全文检索。
